# V11.2 Durable Mutation Gateway

V11.2 turns the V11.1 resident observer into a mutation-capable recovery worker without pretending that GitHub Actions supports provider-level exactly-once execution.

## Durable journal

Each recovery idempotency key is hashed and stored as a JSON record on a dedicated `recovery-state-v112` branch. The gateway writes `PREPARED` before calling GitHub's `rerun-failed-jobs` API and changes the same record to `COMMITTED` only after GitHub accepts the request.

A repeated request with a `COMMITTED` record returns the durable receipt and does not call GitHub again. A repeated request that finds `PREPARED` fails closed as `durable_mutation_ambiguous_prepared`; it does not resend the mutation. This covers the crash window where GitHub may already have accepted the rerun but the gateway did not yet persist the commit record.

## Safety boundary

The gateway advertises durable idempotency and lookup because the logical gateway identity is durably reserved and queryable. It explicitly advertises `physical_exactly_once: false`. GitHub's rerun endpoint does not accept a caller-supplied idempotency key, so V11.2 does not claim provider-level exactly-once semantics.

The ambiguity policy is deliberate: when physical outcome cannot be proven, automatic recovery stops rather than risking a duplicate rerun.

## Runtime permissions

A live V11.2 workflow needs `actions: write`, `contents: write`, `pull-requests: read`, and `contents: read`. The durable journal branch is separate from protected `main` and contains only machine recovery records.
