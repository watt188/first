# V9.5 Idempotent Recovery Gateway

V9.5 binds the V8.8 replay identity and V9.3 durable pending-action journal to a downstream recovery gateway that explicitly supports an idempotency key and lookup by that same key.

## Flow

1. Validate exact PR head.
2. Use the replay key as the downstream idempotency key.
3. If the journal is already COMMITTED, return the committed receipt without another mutation.
4. If the journal is PREPARED after a crash, call `lookup_recovery(idempotency_key=...)`.
5. If the gateway proves an accepted prior mutation with a stable receipt, commit the journal and continue without replay.
6. If the gateway cannot prove the prior outcome, fail closed and keep PREPARED.
7. For a new action, persist PREPARED before calling `execute_recovery(..., idempotency_key=...)`, then COMMIT only after `accepted=true` plus a stable receipt ID.

## Security properties

- Exact-head binding is preserved.
- Duplicate calls with a committed replay key do not issue a second mutation.
- Crash-after-mutation/before-journal-commit can be reconciled without blind replay when the provider retains idempotency state.
- Reusing one replay key with different action/job/attempt identity fails closed.
- Ambiguous PREPARED actions remain unresolved rather than being guessed safe.

## Boundary

V9.5 provides exactly-once *logical* recovery only if the downstream gateway durably honors and can look up the idempotency key. It does not claim exactly-once physical side effects for APIs that ignore the key, lose their dedupe record, or cannot reconcile a prior request.
