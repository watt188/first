# V9.6 Idempotent Recovery Transaction

V9.6 composes the durable recovery state, V8.9 lease, V8.8 replay authorization, V9.3 pending-action journal and V9.5 idempotent gateway into one exact-head transaction path.

## Flow

1. Load or initialize exact-head durable state.
2. Acquire and CAS-persist the recovery lease.
3. Classify the failure and derive the next monotonic attempt.
4. Authorize the replay identity and derive the deterministic replay/idempotency key.
5. Execute through V9.5, which writes PREPARED before the downstream mutation and reconciles prior PREPARED/COMMITTED outcomes by idempotency key.
6. Append accepted evidence to the V8.5 hash chain.
7. CAS-persist the evidence while the lease remains bound.
8. Release and CAS-clear the lease.

## Security properties

- Exact PR head is enforced before mutation.
- Competing workers cannot overwrite a live lease through the durable CAS state store.
- Downstream recovery uses the replay key as an idempotency key.
- Accepted recovery evidence is append-only and attempt-monotonic.
- A committed downstream action can be reconciled after a crash without another logical mutation when the provider retains idempotency state.
- CAS conflicts, stale heads, unresolved pending actions and ambiguous outcomes fail closed.

## Boundary

V9.6 provides an end-to-end logical recovery transaction, not a distributed database transaction spanning GitHub and SQLite. Exactly-once physical side effects still require the downstream provider to durably honor and expose lookup for the supplied idempotency key. Merge authority remains outside this transaction engine.
