# V10.10 Final Production Recovery Convergence

V10.10 composes the production recovery path behind one control plane:

- durable recovery state and journal persistence;
- idempotent recovery transaction/reconciliation;
- authenticated envelopes, replay protection, and rotating HMAC keys;
- live GitHub pull-request head resolution immediately before recovery;
- fail-closed production gateway capability attestation;
- exact-head recovery execution through the existing V10.1 runtime.

The live GitHub head replaces caller-supplied `current_head_sha` before V10.2 validation. A stale expected head or an unavailable/invalid GitHub response rejects the command before external recovery mutation. Gateway readiness requires literal `true` for durable idempotency and lookup-by-idempotency-key plus identified provider and scope.

## Security and durability boundary

This remains a single-host control plane because recovery state, pending actions, authentication key lifecycle metadata, and replay nonces use SQLite. HMAC secrets are runtime-supplied and are not intentionally persisted by this stack. GitHub access tokens are runtime-only inputs.

A gateway capability declaration is an attestation, not cryptographic or empirical proof that an external provider implements physical exactly-once side effects. Logical exactly-once recovery semantics still depend on the downstream gateway durably honoring the supplied idempotency key and lookup contract.

V10.10 does not provide TLS termination, mTLS, distributed consensus, remote secret distribution, hardware-backed key custody, or a deployment supervisor. Those remain infrastructure concerns around the control plane.
